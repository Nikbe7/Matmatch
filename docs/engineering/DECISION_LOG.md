# Decision Log

Append-only record of non-trivial, non-obvious decisions — technical choices, scope cuts, schema calls, process changes. Not a changelog of *what* changed (git history has that) — a record of *why*, so nobody (human or Claude) re-litigates a settled question without knowing what was already considered.

**When to add an entry:** any decision that (a) had a real alternative someone could reasonably ask "why not X instead," (b) would be expensive to reverse, or (c) future-you would want the reasoning for, not just the outcome. Skip routine implementation choices — this is not a diary.

**Format:** newest entry at the top. Keep entries short — a paragraph, not a report.

## 2026-08-16 — Merged "Acceptera" and "Lagad ikväll" into one "Laga ikväll" action; renamed `meal_cooked` to `meal_chosen`

**Decision:** #142 removed Tonight's card chrome to match `lovable-reference/screenshots/tonight.png` and collapsed its two separate actions — "Acceptera" (→ shopping list) and "Lagad ikväll" (record cooked, stay on Tonight with a persistent confirmation) — into one: "Laga ikväll" both calls `POST /api/cooked` and navigates to `/lista`, in that order, in the same tap. The disabled-button/"Lagad ✓" confirmation state is gone entirely; there is no longer anything on Tonight to confirm. If the `/api/cooked` call fails, navigation to `/lista` still happens — the UI swallows the error silently rather than showing it, since a failed history write is nothing a household can act on and must never block them from shopping. The frontend analytics event fired at this moment is renamed from `meal_cooked` to `meal_chosen`, with the same fields (`templateId`, `rerollDepth`); a new `meal_choice_history_failed` event (`templateId` only) is fired instead of `meal_chosen` reporting failure, so the two facts — "the household chose this dish" and "the suppression write for it didn't land" — stay separately queryable. Both the web and backend (`src/api/routes/analytics.ts`) event vocabularies were updated together, since the backend's schema is a closed mirror of the frontend's by design (2026-08-05 analytics entry's structure). `POST /api/cooked` and the `cooked_meals` table are unchanged — their purpose (suppress this dish from ranking for about two weeks) is unaffected by what triggers the call or what the analytics event is called.

**Why:** The reference has no separate "mark as cooked" step — choosing the dish *is* the confirmation, and matching it required removing that second action, not just restyling it. But the app had never before recorded "cooked" on anything but an explicit, separate confirmation; firing the same `meal_cooked` event at plain choice-time would have silently changed what the event means without changing its name, which is exactly the kind of quiet metric drift that makes Phase 2 numbers (Weekly Active Deciders, repeat-use rate) uninterpretable later without someone remembering this decision. Renaming forces every future reader of the analytics data to ask "chosen or actually cooked?" rather than assume the old answer. The known cost: a household that taps "Laga ikväll" and then orders pizza instead still produces a `meal_chosen` event and a `cooked_meals` row that suppresses the dish from ranking for two weeks, exactly as if they'd cooked it — there is no cheap way to distinguish "chose and cooked" from "chose and changed their mind" without adding a second confirmation step, which is the exact UI the reference and this merge deliberately remove. Idempotency of `POST /api/cooked` was verified against the real route (`src/api/routes/cooked.ts`, `src/db/cookedMeals.ts`) before this could be approved: the `(household_id, template_id, cooked_on)` unique constraint with `on conflict do nothing` collapses repeat taps for the same dish on the same day into one row, so no new dedup logic was needed on the client.

**How to apply:** Anyone reading `meal_chosen` counts for Phase 2 metrics must treat it as "the household picked this dish," not "the household cooked this dish" — the two diverged the moment this shipped. If a future feature needs to know whether a dish was *actually* cooked (as opposed to chosen), that needs a new, separate signal — don't repurpose `meal_chosen` or the `cooked_meals` table for it without a fresh decision. The Tonight suggestion itself lost its card wrapper as part of the same change; the general rule (a card groups lists and collapsible blocks, never a screen's own main content) is recorded in `docs/UX_FLOW.md` §10 and applies to the rest of the Tailwind-v4 migration, not just this screen.

## 2026-08-15 — Adopted `react-router-dom` for the app shell's four routes

**Decision:** `web/` adds `react-router-dom` (v7, `BrowserRouter`) and moves from `App.tsx`'s hand-rolled `view` state machine to four real routes — `/` (Tonight), `/bygg` (guided flow), `/lista` (shopping list), `/profil` (account) — each reachable by URL, with a shared bottom navigation. Not TanStack Router (already ruled out, 2026-08-12 entry) and not a home-rolled path-matcher.

**Why:** The bottom nav (#137) needs each tab to be a real, bookmarkable, back-button-aware destination — in particular, the shopping list must be resumable at its own URL when a household reopens the app mid-shop (UX_FLOW §7), which a `view` variable in component state cannot give a browser's history stack or a page reload. `react-router-dom` is the boring, standard choice for this in a Vite + React SPA; the alternative (extending the existing state machine with manual `history.pushState` calls) is more code for a worse version of what the library already does correctly, including the server-side SPA fallback the backend (`src/api/static.ts`) already serves for any unmatched path.

**How to apply:** All four top-level screens are routes under one `BrowserRouter`, mounted once inside `Gate` so route changes never remount the analytics sink or the offline/error/loading states, which stay rendered directly by `Gate`'s own status, independent of the current route. Routing must not spread further than these four screens — no nested/child routes without a fresh decision.

## 2026-08-11 — Ingredient swaps shipped without the dish-level cost tier or the AI fallback (#124)

**Decision:** #124's popover (Billigare/Liknande filters plus a role-valid search over curated substitution groups) shipped as scoped, but two pieces named in the original spec were cut and filed separately rather than settled inline. First, a swap never recomputes the dish's own `cost_tier` — DECISION_LOG 2026-08-01 already left that undefined, and inventing an answer inside a UI slice would have been exactly the quiet architectural call CLAUDE.md rules out; each alternative shows its own curated tier instead, and #131 tracks defining the real rule. Second, the "Föreslå alternativ (AI)" fallback for the 86 (of 744) substitutable slots with zero curated alternatives was deferred as #132: those are a curation gap, not a product gap, and #132 asks whoever picks it up to weigh an additive substitution-group pass against an AI call before building the AI path by default.

**Why:** both cuts came from spotting that "AI is for language and for gaps in curated data" (2026-08-10) was about to be violated by the wrong entity. A missing dish-tier rule isn't a language gap — it's an engine question this slice had no mandate to answer. Missing curated data for common ingredients (ägg, avokado, majs, svartpeppar) is a curation gap, and curating it once benefits every future request for free, unlike an AI call that's paid per-request forever.

**How to apply:** don't add a swap-driven cost-tier recompute anywhere until #131 lands. Don't build #132's AI fallback without first estimating how much of the 86-slot gap a curated pass would close.

## 2026-08-11 — Missing defining ingredients added to 12 templates; the derived cost_tier rule flips on one mid ingredient (#129)

**Decision:** Investigating a uniform-looking `ingredient_slots.length` distribution across the 170 templates (asked ahead of #124) found the count uniformity itself was fine — Swedish/nordic dishes genuinely average fewer slots than asian ones, and every 4-slot template checked was complete at four — but turned up a real, different gap: `fat_oil` was used in 0 of 903 slots, and 0 of 36 `italian_mediterranean` templates contained olive oil, including **Pasta aglio e olio** ("garlic and oil," no oil) and **Melanzane alla parmigiana** (no parmesan). Fixed additively across exactly 12 templates in two groups: definitional omissions (`pasta-aglio-e-olio-med-prastost` + olivolja; `melanzane-alla-parmigiana` + parmesan + olivolja; the four pie/risotto dishes + smör, three of them + ägg as the filling's binder; three fried breakfast dishes + margarin) and buy-it-or-you-can't-cook-it deep-frying dishes (`fish-and-chips-med-torsk-och-remouladsas`, `friterad-tofu-i-sotsur-sas-med-ananas` + rapsolja).

**The fat choice rule:** where a dish is genuinely made with either a premium and a budget fat, the cheaper true option is not tier-gaming — it's the more accurate answer for an everyday dish. Pannkakor, våfflor and raggmunk got `margarin` (budget), not `smör`, for exactly this reason and stayed at `budget`. Where the fat is definitional (the pie crusts, risotto, `aglio e olio`'s olive oil), the correct ingredient was added and the tier consequence accepted.

**One `cost_tier` flip, computed before editing rather than discovered by a failing validator:** `melanzane-alla-parmigiana` mid → premium, because `parmesan` (premium) now outranks `mozzarella`/`tomat` (mid) under the existing highest-slot-tier rule (DECISION_LOG 2026-07-31). Every other addition in this pass left its template's tier unchanged — most because the dish's `budget`/`mid` ceiling was already set by another slot.

**Named but not fixed here:** deriving `cost_tier` as the highest tier among slot ingredients is a blunt rule — one `mid`/`premium` ingredient can flip an otherwise cheaper dish, regardless of how small a role it plays. This pass produced one instance of that; a future audit should expect more, not treat each one as a surprise.

**Explicitly out of scope, stated in #129 before implementation:** the same audit found ~20 additional wok/stekt/rostad templates missing a cooking or frying fat, and none of them were touched. Padding every fried or sautéed dish with an oil line adds a shopping-list item every household already has, for no benefit — the reason #128 (a pantry-staple concept the list can suppress) is filed as the prerequisite for doing that broadly. This entry is the record that the wider set was found and deliberately left alone, not missed.

**How to apply:** #128 must land, and the suppression mechanism it designs decided, before adding cooking fat to the ~20 stir-fry/roast templates the audit also flagged. Until then, a new template that's genuinely fried should still name its fat — the point of this pass was accuracy on the *defining* cases, not a blanket ban on `fat_oil` slots.

## 2026-08-11 — Ingredient quantities: 8-unit vocabulary, 4-portion reference, per-unit rounding (#123)

**Decision:** Every `IngredientSlot` carries a required `quantity` — either an amount in a closed 8-unit vocabulary (`g`, `dl`, `msk`, `tsk`, `krm`, `st`, `klyfta`, `kruka`) or the explicit `{kind: "to_taste"}` marker, with the validator rejecting a slot that has neither so a missing amount fails rather than defaulting. Amounts are authored for **4 portions**, the unit Swedish recipes are written in — which is what made ~900 drafted numbers reviewable against a familiar register, and is why reference 1 (trivial scale factor, per-person amounts nobody writes) lost. Volume is dl/msk/tsk because that is how a Swedish kitchen measures; `st`, `klyfta` and `kruka` exist because the catalog names the product rather than the portion of it a dish uses ("2 st vitlök" would be two bulbs, and herbs are sold in pots). `krm` is restricted by an authoring rule, not just by taste: only for spices where the amount changes the outcome and you cannot taste your way there (saffran, muskot, kanel, cayenne, malen ingefära) — salt, svartpeppar, chiliflakes and anything adjusted at the stove stay `to_taste`, because "2 krm salt" on a shopping list is an amount nobody acts on and a few of those make `to_taste` meaningless. Scaling is linear against the reference and lives only in `scaleSlotQuantity` (`src/engine/quantities.ts`), which rounds per unit: grams to 10 below 100 g and to 50 above, dl/msk/tsk to the nearest half, and `krm`/`st`/`klyfta`/`kruka` to whole — every unit with a floor, so a small household is never told to use nothing. The rule exists so the number is buyable: 500 g at 1.1 portions is 137.5 g linear, and 150 g is what goes on the list. The quantity belongs to the slot, not the ingredient, so a substituted slot keeps its amount.

**The data pass:** all 903 slots across 170 templates drafted in four batches with the validator run against each, then a stratified 22% sample (38 templates, every protein_group × cuisine cell) hand-checked. Four corrections: `formbröd` at 4 st for the two burger dishes and the cheesesteak (a burger needs two slices per portion, and the other sandwich dishes were already at 8), and ärtsoppa's dried peas 500 g → 400 g. An automated consistency sweep alongside the sample normalised `makaroner` to grams in three templates (it had been mixed dl/g — pasta is bought by weight) and flagged seven "light" protein slots that were all correct as authored: bacon, wrapped skinka, shrimp beside cod, cheese as flavouring. Final distribution: 316 g · 260 st · 128 dl · 55 msk · 51 kruka · 45 tsk · 38 klyfta · 3 krm · 7 to_taste. The `krm` count being 3 (kanel ×2, muskotnöt ×1) and `to_taste` being exactly svartpeppar and chiliflakes is the check that the authoring rule held.

**How to apply:** a new template must state a quantity per slot at 4 portions, picking `to_taste` whenever the amount is adjusted at the stove rather than bought to a number. Never add a unit to the vocabulary to fit one dish — express it in an existing unit or use `to_taste`. If a rounding band ever changes, change it in `ROUNDING_RULES` only; no surface may round an amount itself, and no model may produce one at request time.

## 2026-08-10 — Perceived intelligence comes from surfacing the engine's reasoning, not from more AI

**Decision:** Where the app should feel smart, the answer is to expose what the deterministic engine already computed — not to add a model. `rankCandidates` already knows why a dish won (seasonality, familiarity, recency, pantry coverage) and the catalog already carries curated cost tiers per ingredient; none of it is visible, so considered decisions read as arbitrary ones.

**Three rules this settles:**
1. Intent belongs on the ingredient, not the dish. "Billigare" at dish level is ambiguous; tapping lax and asking for cheaper is exact — same role, lower `default_cost_tier`, no model involved.
2. AI is for language and for gaps in curated data. Never for numbers, never for safety, never for ranking. An AI alternative is a fallback that must be unreachable while curated data can answer.
3. Quantities are curated data. Portion scaling currently promises something the templates cannot deliver, so quantities are added by an offline drafted-and-spot-checked pass, never generated at request time.

**Why not more AI for feel:** a chip that returns a dish in 50ms beats one that takes four seconds to look sophisticated. Simplicity is the feature; the differentiator against a chat assistant is that a change propagates — shopping list, allergy gate, cost tier and scaled quantity all update — not that the app can hold a conversation.

## 2026-08-10 — Allergy handling is done after two more small changes; onboarding stops asking up front

**Decision:** Allergy support stays — the verified 206-row mapping is Phase 0's heaviest asset and a household food app that ignores allergies is unserious. But the posture changes, and allergy work stops after two remaining changes: (1) onboarding no longer asks for allergies — a household is people, and allergies/dietary flags become optional attributes added when the user chooses to, not a gate before the first suggestion, per UX_FLOW §1 (prove value before asking for detail); (2) a chosen dish warns and offers a swap rather than being hidden — a nut-allergic diner selected against a dish naming nuts shows a named warning and a role-matched substitution suggestion from the existing substitution groups, no blocking.

**Unchanged:** what the app *proposes* is still filtered silently and deterministically — Tonight and the direction cards make a claim, and that claim must be safe. What the user *asks for* is never hidden. That split is already recorded (2026-08-09, push vs pull) and this entry does not reopen it.

**How to apply:** after these two land, no further allergy machinery until real users show it's needed. The recurring cost was never the data — it was weaving filtering through every new surface.

## 2026-08-09 — Allergies and dietary flags move onto HouseholdMember; §5's "not per-member" line reversed (#115)

**Decision:** `allergies[]` and `dietary_flags[]` are declared per household member, not per household. The household-level columns are dropped, not kept in sync; the effective constraint set is derived on demand (`mealConstraints`, `src/engine/constraints.ts`) and never stored. `HouseholdMember` also gains an optional `name`.

**Why:** this reverses ARCHITECTURE.md §5's "shared across the household, not per-member." A household does not have allergies; people do, and the union discards *whose* a restriction is — the fact #112 (constraints scoped to who is eating tonight) needs and cannot get from a union with no owner.

**Why not keep both:** two stores of a safety-critical value drift, and the stale one is the one that gets read — the same reason §5.3/§5.5 forbid allergen data on templates or substitution groups.

**Conditions:**
1. Both member arrays are required with no default at either layer (zod or Postgres), so an omitted value errors rather than silently meaning "no allergies" — §5.4's `verification_status` reasoning, one level down.
2. A data migration verified only by `supabase db reset` has not been verified — it runs the backfill over zero rows. Exercise it against planted pre-migration rows in a scratch database.

## 2026-08-09 — Tier 2 generation: exact-match resolution, household-free cache key, unverified-content rule (#113)

**Resolution is exact match only, in two normalized forms — never fuzzy.** `src/engine/generatedDish.ts`'s `resolveIngredientName` normalizes a model-proposed name (NFC, lowercase, trim, collapse whitespace) and matches it against an index of the catalog's normalized ingredient names; on a miss it falls back to an ascii-folded, hyphenated form matched against `ingredient.id` (the catalog's ids are already ascii slugs of their Swedish names — `src/schema/ingredient.ts`'s `SlugIdSchema` comment — so this fallback exists specifically to catch a model that reproduces a name without its diacritics, e.g. "gul lok" for "gul lök"). Levenshtein, substring, or prefix matching was considered and rejected: a fuzzy match that succeeds *wrongly* silently attaches the wrong verified allergen row to an ingredient — "mandel" (tree nuts) vs "mandelmjölk" (also tree nuts, but a different catalog row and a different real product), "ost" vs "getost" — and that is a fail-*open* failure no test can reliably catch, since the test would have to predict which wrong pair the model happens to propose on a given run. Exact matching keeps the only possible failure mode "unresolved," which is fail-closed and already has a rule (below). Recall — the model dropping words or paraphrasing — is solved on the prompt side instead: `src/ai/dishPrompt.ts` gives the model the full catalog as a closed vocabulary and instructs it to copy names verbatim, so the matcher doesn't need to be forgiving to get reasonable coverage.

**The cache key carries no household data, and that is provably safe rather than merely asserted.** `generated_dishes` (migration `20260809000000_tier2_dish_generation.sql`) is keyed on `(generator_version, query_key)` — `query_key` a normalized query phrase (`src/db/generatedDishes.ts`'s `buildQueryKey`), `generator_version` a constant bumped whenever the prompt, output schema, or resolution algorithm changes. What's cached is the model's raw, schema-validated output — never a resolved-and-safety-checked result. This is safe not because the key happens to omit allergy fields, but because **no household data reaches generation at all**: the prompt (`buildDishPrompt`) receives only the query and the catalog's ingredient names, nothing about who's asking. Resolution and the allergy/dietary gate (`resolveGeneratedDish`, `isGeneratedDishVisibleToHousehold`, `passesHardDietaryFilter`) run fresh against the cached output on *every* read, for *every* household — so a cache hit cannot itself change the applicable allergy outcome, because the safety decision was never stored in the first place. Verified directly, not just by construction: `dishGenerate.test.ts`'s cross-household test generates one dish from a peanut-allergic household (a cache miss, so it also writes the row), confirms it's withheld, then reads the identical cached row from a household with no allergies and confirms it's shown — one Anthropic call, two correct and opposite outcomes.

**Unverified content follows the existing §5.4 fail-safe rule, extended rather than re-invented.** A generated dish with any unresolved ingredient is withheld from any household with a declared allergy, and may be shown (marked `unverified: true`) to a household with none — the same "missing/unverified mapping row is treated as containing every allergen" posture `effectiveAllergens` already applies to a single ingredient, just triggered by "we don't know what this ingredient even is" instead of "we know the ingredient but not its allergens." A *resolved* ingredient still goes through the ordinary `isIngredientExcluded` check, so a fully-resolved dish naming a known allergen is withheld outright — Tier 2 dishes carry no substitution groups in this slice, so there is no rescue path once an ingredient is excluded. Cost tier and `high_protein_preference` are derived exactly the way the validator already derives them for curated templates (`src/tools/validation.ts`'s highest-cost-tier and no-starch-slot rules) — from *resolved* ingredients only, `undefined`/not shown when any ingredient is unresolved, never taken from the model. `dietary_tags` on a generated dish can only ever be `[]` or `["high_protein_preference"]`: there is no per-ingredient animal-origin fact in the catalog to derive `vegetarian`/`vegan` from, so a generated dish always fails the existing hard dietary filter (`passesHardDietaryFilter`, exported from `src/engine/candidates.ts` for exactly this reuse) for a household declaring either — correct and fail-closed for this slice, not a gap; a follow-up issue covers adding a curated animal-origin flag to lift it.

**Global daily generation ceiling ships with this slice; the per-user monthly cap does not.** DECISION_LOG 2026-08-05 requires both a per-user cap and a global spend ceiling before Tier 2 ships, "neither optional." This slice satisfies the global half with a sliding-24-hour-window count against `dish_generation_attempts` (one row per *attempted* call, recorded before the Anthropic request so a timeout or API error still counts against spend) — degrading cleanly to `{ dish: null, reason: "generation_limit" }`, never a 5xx or unmetered spend. The per-user monthly cap is explicitly deferred to the separate freemium-gating slice issue #113 scopes it out to, since it's a product/billing concern (who gets how many, by tier) rather than a spend-safety one.

**How to apply:** any future free-text-to-structured-data resolution against curated data should default to exact match plus a documented normalization fallback, not fuzzy matching, when a wrong match is worse than a missed one — this generalizes beyond ingredients. Any future AI-response cache should ask "does household/user data actually reach the model?" before deciding what the cache key needs to encode — if the answer is no, the key needs nothing to enumerate and the safety check belongs entirely on the read path, not the write path.

## 2026-08-09 — Constraints come from who is eating tonight, not from the household as a whole

**Decision:** Allergy and dietary filtering is applied against the set of household members actually eating a given meal, not the household's union of constraints. The default is everyone; changing it is one tap and never a required step.

**Why:** the union is wrong most nights. A household containing one peanut-allergic child cannot be shown any peanut dish, ever, even when that child is at a grandparent's. Keying constraints to the diners makes those dishes legitimately suggestible rather than reachable only through a warning — it converts a permanent restriction into an accurate one, without weakening anything.

**Conditions:**
1. The default diner set is every household member. Safety must be the default state, never something the user has to select.
2. Selecting diners must not become a gate before the first suggestion. The Tonight card stays zero-input and assumes everyone; diner selection is an adjustment, not a step.

**Implementation (#112).** `mealDiners(members, diners?)` in `src/engine/constraints.ts` is the only exported way to obtain a constraint set for a request; `householdConstraints` is gone rather than left as a second door. It resolves the diner set once and derives constraints *and* portions from that single resolution, so no route can filter for one group and cook for another. Resolution is fail-closed with no error path anywhere: absent, empty, non-integer, negative, out-of-range, or a set that is merely *mostly* valid all resolve to the whole household, and `src/api/diners.ts` returns `undefined` rather than throwing a 400 for any malformed `diners=` parameter. This deliberately departs from the `parseWeightsFromQuery`/`parseExcludeFromQuery` idiom of rejecting wrong-typed input: two rules on one safety-critical parameter is the seam a later edit slips through, and the safe answer is always available, so a client bug should widen the constraint set rather than dead-end the household. Both guided endpoints take their diner set from `createGuidedClient` (`web/src/guidedClient.ts`) and neither accepts one as an argument — a grid built for one set and directions for another is inexpressible rather than merely discouraged. **The known cost is positional identity:** a member is its index (no per-member id, per the #115 entry above), so a selection is only meaningful against the roster it was made on. Closed now rather than deferred to whoever builds member editing: the client resets the selection to everyone whenever the roster it renders changes (`useDinerSelection`, keyed on the member labels), and the server range-check catches the out-of-range half — an index that shifts but stays in range is the half the reset covers.

## 2026-08-08 — Guided flow's intent chips map onto existing engine levers only; no new ranking dimension, and "Matlådor" is not shipped (#107)

**Decision:** The guided quick-select flow (UX_FLOW §5) selects directions with `selectCandidateTemplates` and `rankCandidates` **unchanged**. A new pure module `src/engine/directions.ts` composes on top of them — main-ingredient filter, pantry-coverage bucketing, cuisine variety — and never scores. Each intent chip resolves to a lever that already exists: `Middagsidé` → the default `{cost: 0, time: 0}`; `Billigt` → `{cost: 3}`, i.e. `WEIGHT_LEVELS[2]`, where a maxed "Billigare" chip already ends up; `Använd det jag har` → neutral weights, its whole lever being the pantry step; `Proteinrikt` → a *selection preference* for `high_protein_preference`-tagged candidates within the ranked order; `Överraska mig` → neutral weights, with the flow skipping steps 2 and 3 and the engine reading the main ingredient off the top-ranked candidate. **`Matlådor` is deliberately not shipped** (#108).

**Why:** `rankCandidates` is the single source of ordering truth for the whole product, and Tonight and the guided flow must never disagree about what is safe or what ranks higher. Adding a pantry or protein term to `scoreCandidate` would have made them disagree structurally — every constant in that file is calibrated against the others (see `FAMILIARITY_STEP_WEIGHT`, `RECENCY_PENALTY_WEIGHT`), and a new term means re-deriving all of them for a signal only one screen has. Selection on top of the ranked order is not a new idea here: `pickNextSuggestion` already applies protein/cuisine diversity the same way, without touching a score. The guided flow legitimately answers differently from Tonight only because the household handed it input Tonight never asked for.

`Proteinrikt` had no lever at all: `high_protein_preference` is a soft dietary flag that `selectCandidateTemplates` explicitly refuses to hard-filter on and that `scoreCandidate` has no term for. Hard-filtering was rejected — 13 of 170 templates carry the tag before allergies are applied, so it is an empty screen waiting to happen, and it would reverse the 2026-07-31 decision that put the flag in ranking's half of the world. A preference keeps both decisions intact and still makes the chip do something real.

`Matlådor` was cut rather than faked. It needs two things that do not exist: a lunch-box count on the `Household` schema (UX_FLOW §3 asks for it in onboarding; it was never built) and a keeps/reheats signal — `meal_types` including `lunch` is a different claim, and reaching for it would also mean parameterizing the hardcoded `"dinner"` in `selectCandidateTemplates`, a shared-engine change Tonight depends on. Five chips that each do something beat six where one quietly behaves like `Middagsidé`.

Two smaller calls in the same slice. **Pantry input travels as a query parameter and is stored nowhere** — no table, no localStorage, no analytics payload — per CLAUDE.md's session-scoped non-negotiable; the session ingredient ids appearing in a URL (and so in any access log) was accepted as not sensitive, and GET symmetry with `/api/tonight` was judged worth more than hiding them in a request body. **The card's one-line description is derived, not authored and not generated**: templates store structure rather than prose, adding a `description` field was out of scope, and an AI-written line is the follow-up Tier 1 slice's job — so the line states the dish's protein, starch and lead vegetable, using the substituted ingredient wherever a slot was rescued.

**How to apply:** a new intent chip must name the existing lever it pulls before it is built; if there isn't one, cut the chip and file the issue for the data it needs, as #108 does. Do not add a pantry, protein or "meal prep" term to `scoreCandidate` — if a future flow genuinely needs one, re-derive every constant in `src/engine/ranking.ts` against it in the same change, and expect Tonight's output to move. `directions.ts` is downstream of the safety filter by construction and must stay there: it selects from a set that is already safe and may never widen one.

## 2026-08-07 — One Node service serves client + API from one origin, on Fly.io in `arn`; and a class of bug no local test can catch (#99)

**Status (2026-08-07): built and merged, deliberately not deployed.** The hosted Supabase project exists with all migrations applied, but no Fly app has been created — deployment is deferred until after a round of UI/UX iteration against DevTools mobile emulation, and is gated on adding a payment method to the Fly account (#99). Everything below describes the shape that is in the repo and tested, not a running system.

**One service, one origin, one process.** The image runs the same Express app that serves `/api/*` and additionally serves `web/dist` as static files, with an SPA fallback for unknown non-`/api` paths. No nginx, no CDN, no separate static host — which is what keeps CORS permanently unnecessary (`web/vite.config.ts` has documented this intent since the frontend existed) and means a deep link or a reload on one renders the app rather than 404ing. Static serving is mounted *inside* `createApp` via an optional `webDistDir` dependency rather than bolted onto `server.ts`, because `errorMiddleware` is registered last and ordinary middleware added after it would never be reached. When `webDistDir` is absent — local development, every existing test — the app is API-only and behaves exactly as before; `npm run dev` and the Vite proxy are untouched. **Why not a separate static host + API host:** two origins means CORS, a second deploy target, and a preflight on every API call, to save nothing at this scale.

**Fly.io, `arn` (Stockholm), always-on.** `auto_stop_machines = false` with `min_machines_running = 1`: a scale-to-zero setup would pay a cold start on nearly every request for a once-a-day meal app, and the health check (`GET /health`) deliberately touches neither the database nor the engine data, so a paused free-tier Supabase project or a DB blip cannot fail the check and put Fly into a restart loop on a service that is itself fine. Region `arn` sits next to the Supabase project's `eu-north-1`, keeping household and allergy data — sensitive personal data under GDPR (ARCHITECTURE.md §7) — in the EU and the app next to its database.

**`tsx` moved from `devDependencies` to `dependencies`.** The backend has no build step and runs its TypeScript directly, so in a production image `tsx` is a runtime dependency, not tooling. The alternative — shipping the entire dev tree (vitest, the Supabase CLI, workbox) into the image so one binary is present — is worse on every axis.

**`VITE_*` are baked at image build time, not read at runtime.** Vite substitutes `import.meta.env.VITE_*` into the bundle during `vite build`, so `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are Docker build args, and **changing them requires a rebuild and redeploy — a `fly secrets set` plus restart does nothing**, because the values are already compiled into the JavaScript. Both are public by design (the anon key ships in browser bundles and the Data API is disabled), so nothing sensitive is passed as a build arg, which matters because build args are recoverable from image history. The database password and any Anthropic key are runtime secrets in Fly's store only, and the boundary was verified by grepping the built bundle inside the image rather than asserted.

**The bug worth remembering: hosted Supabase and local Postgres disagree on the RLS default, and no local test can catch it.** `20260805000000_recipe_instructions.sql` deliberately leaves the Tier 1 instructions cache un-RLS'd (it holds no household data and no user context) — but it achieved that by *omission*, simply never calling `enable row level security`. That is correct only where RLS defaults to off. A hosted Supabase project auto-enables RLS on new tables in `public`, so the identical migration produced `relrowsecurity = t` with **zero policies** in the cloud, and `matmatch_app` has no `rolbypassrls`: inserts failed with "new row violates row-level security policy" and selects returned 0 rows. The cache would have been silently dead in production while every local test passed, because the suite runs against the local stack where the default happens to be the one we wanted. `20260807000000_recipe_instructions_disable_rls.sql` disables it explicitly, which converges both environments and implements the existing 2026-08-05 decision rather than making a new one. **Why not add permissive policies instead:** that would invent per-row rules for a table with deliberately no per-row owner.

**How to apply:** never rely on a *default* to produce a security-relevant table property — state it explicitly in the migration, because "what the migration does not say" is exactly what varies between the local stack and the hosted project. This is a general class, not a one-off: local Supabase and hosted Supabase are not the same Postgres configuration, and the test suite only ever sees the local one. After any migration that adds a table, verify its `relrowsecurity`/`relforcerowsecurity` and its grants **against the hosted project** as the `matmatch_app` role — an unfiltered `select` returning zero rows there is the signature, and it is silent by construction. The `⚠ Adding a table?` warnings in README.md and `20260803120000_least_privilege_app_role.sql` cover the missing-grant and missing-`TO`-clause traps; this is the third member of that family.

## 2026-08-07 — `peak_months` means Swedish-retail "at its best and cheapest now," not global growing season or bare purchasability (#50)

**Decision:** Re-derived `available_year_round`/`peak_months` for all 206 catalog ingredients. Before this, only 2 were seasonal (`kantarell`, `nypotatis`), so `SEASONALITY_WEIGHT` in `src/engine/ranking.ts` was effectively inert — only 5/170 templates contained any seasonal ingredient at all, and in-season fraction barely moved ranking. #50's own suggested resolution (2) is the one taken: `available_year_round: false` + `peak_months[]` expresses "this is at its best and cheapest in a Swedish shop right now," not "importable in December" — a Swedish shop stocks imported tomatoes in February, but `tomat` peaks `[7,8,9]` because that's when the Swedish-grown, cheap, good version is around. 39 of 206 ingredients ended up seasonal (19%); 167 stay `available_year_round: true` — genuine staples (rice, pasta, flour, dairy, most meat, oils, dried spices, imports with no Swedish season like citrus/bananas/peppers) were deliberately left alone rather than manufacturing a seasonality signal for them. Coverage moved from 5/170 to 83/170 templates (49%) containing at least one seasonal ingredient. Drafted in one pass against personal Swedish-grocery knowledge (protein: lamb, mussels, cold-water shrimp; produce: brassicas, roots, courgette/tomato/cucumber family, berries, stone fruit, asparagus, new potatoes; a couple of aromatics: leek, fresh dill), then spot-checked by hand against a 20% stratified-by-category sample (#7's precedent for this class of data) — the spot-check itself caught a real bug: three imported, genuinely non-seasonal vegetables (`aubergine`, `gron-paprika`, `rod-paprika`) had been left with a stale `seasonality_strength: "strong"` from before this pass despite being `available_year_round: true`, corrected to `"weak"`.

**New validator invariant, `IngredientSchema` (`src/schema/ingredient.ts`):** `available_year_round: true` now requires empty `peak_months`, mirroring the existing reverse rule (`false` requires at least one entry). The two fields could previously contradict each other silently — 18 catalog rows already did, e.g. `tomat` was `available_year_round: true` with `peak_months: [7,8,9]` — which is exactly the ambiguity between "purchasable" and "at its best" this decision resolves; the validator now makes that contradiction a hard error instead of a readable-either-way row.

**Why not populate `peak_months` on top of `available_year_round: true` instead (§5.1's original shape allowed it):** that shape is what let the ambiguity exist unenforced for 18 rows already, and `inSeasonFraction`'s `available_year_round || peak_months.includes(month)` means a `true` row is already in-season in every month regardless of `peak_months` — a non-empty array on a year-round row is dead data that reads as meaningful and isn't. Forcing the fields mutually exclusive makes each ingredient state one thing.

**How to apply:** Any new catalog ingredient (#46 or later) must pick one of exactly two shapes — `available_year_round: true` with `peak_months: []`, or `available_year_round: false` with a Swedish-retail peak window — and the validator now rejects anything else. Ask "does Swedish retail genuinely have a best/cheapest window for this, distinct from year-round import availability" before marking something seasonal; don't manufacture a window for staples or pure imports just to feed the ranking signal. No change to `SEASONALITY_WEIGHT` or `src/engine/ranking.ts`'s formula — this was a data-coverage gap, not a scoring bug, exactly as #50 characterized it.

## 2026-08-07 — Offline white screen root cause: `Vary: Origin` breaks cache-match for the JS bundle; precaching made per-entry; one Playwright test added (#93)

**Root cause, found only by a real browser (Playwright), not by code review:** the dev/preview server sends `Vary: Origin` on every response. A `<script type="module" crossorigin>` load is a CORS-mode fetch carrying a real, browser-set `Origin` header no script can read or reproduce; the precached entry's key (recorded via `cache.put(url, response)` from a plain string, ending up `mode: "no-cors"` with no Origin recorded) doesn't Vary-match against it. `cache.match(request)` therefore silently missed on exactly the app's own main bundle — an `<img>`/`<link>`-loaded asset (no `crossorigin`, no CORS mode) never hit this and worked fine, which is why only the JS bundle failed and every other precached file was served correctly. Fix: `{ ignoreVary: true }` on both `cache.match()` calls in `handleFetch` (`web/src/sw.ts`) — correct on the merits, not just a workaround, since a content-hashed precached file has exactly one valid response and was never meant to vary by request headers at all.

**Two rounds of manual/curl-based verification (2026-08-06) failed to find this** because nothing about it produces a non-200 anywhere: the file fetches fine standalone, the URL is genuinely present in the precache manifest, and `cache.match()` called with a plain string or a hand-constructed `Request` from `page.evaluate()` both succeed too — a JS-constructed Request can't carry the real, browser-internal Origin header a native `<script>` tag's fetch does, so nothing short of an actual browser executing an actual `<script crossorigin>` load reproduces the mismatch. This is the concrete case behind "recurring theme: failures invisible without a real browser."

**Precaching made resilient per-entry (`web/src/sw.ts`'s `precacheShell`), replacing `cache.addAll()`.** `Cache.addAll()` is all-or-nothing per spec: one failing URL rejects the *entire* install, the worker never activates, and — as with the Vary bug above — nothing surfaces in the Network panel to explain why. `precacheShell` now fetches and `cache.put()`s each entry independently via `Promise.allSettled`, logging (`console.error`) and skipping any entry that fails rather than aborting the whole worker. `registerServiceWorker.ts`'s registration failure and `sw.ts`'s install/activate handlers now also `console.error` on rejection, so a future failure of either kind is visible in DevTools instead of silent.

**One Playwright test (`web/e2e/offline.spec.ts`), not a broader E2E suite.** `@playwright/test` is a new devDependency, deliberately scoped to exactly one flow: load the page, assert `navigator.serviceWorker.controller` is non-null (i.e., the worker actually reached "activated" and claimed the client), go offline, reload, assert the shell rendered. `web/playwright.config.ts`'s `webServer` builds and serves the app itself, so the suite is self-contained (`npm run test:e2e`). Deliberately *not* wired into `npm test` — it's slow (real build + real browser) and needs a browser binary (`npx playwright install chromium`) that the fast unit suite shouldn't depend on. `web/vite.config.ts`'s `test.exclude` keeps vitest from also trying to run files under `e2e/`.

**How to apply:** any future change to `sw.ts`'s cache-matching logic must keep `ignoreVary: true` on precached-shell lookups — see the regression test in `sw.test.ts` ("ignores Vary when matching..."). Before trusting a service-worker change is correct, run `npm run test:e2e` in `web/`, not just the unit suite — `sw.test.ts` exercises the pure logic in isolation and cannot, by construction, catch a real-browser-only mismatch like this one.

## 2026-08-05 — Analytics event ingest: `analytics_events`, closed vocabulary, drop-on-failure (#91)

**Append-only storage, same shape as `cooked_meals`.** `analytics_events` stores household_id, event_name, payload (jsonb), client_timestamp, server_timestamp — `matmatch_app` has SELECT and INSERT only, no UPDATE/DELETE, RLS scoped through household_id with the role in every policy's TO clause (the 2026-08-03 trap). Two timestamps rather than one: client_timestamp is when the tap happened, server_timestamp is when the batch landed, and the sink's flush interval means a burst of buffered events can arrive together but did not happen together. No DB-level event-name enum — the closed vocabulary is enforced at the API layer instead (see below), so extending it never needs a domain-altering migration the way `allergy_value` does.

**Closed vocabulary, validated server-side, whole-batch rejection.** `src/api/routes/analytics.ts` mirrors `web/src/analytics.ts`'s `AnalyticsEvent` union as a zod discriminated union — the same relationship `SessionWeights` (`web/src/api.ts`) has to `RankingWeights`, and for the same reason: the backend can't import browser-only frontend types, and the frontend can't import Node-reaching backend types, so one side duplicates the other's shape rather than either importing it. An unrecognised event name, or a payload with an extra field beyond the fixed shape, 400s the *entire* batch before any row is inserted — a typo that lands as data is worse than an error that surfaces on the first request that sends it, and a partially-stored batch would be a subtler version of the same problem.

**Drop-on-failure, no retry queue, no third-party dependency.** The frontend sink (`web/src/analyticsSink.ts`) buffers in memory, flushes on a 10s interval and on `pagehide`, and drops the batch on any fetch failure — swallowed, never retried, never persisted to `localStorage`. A retry queue would need its own bounding logic to avoid growing unboundedly offline, which is exactly the problem the buffer cap (drop-oldest past 50 events) already solves one layer up; adding retry on top would reintroduce it. This is pre-PMF, low-volume, internal-metrics-only data — losing a session's worth of taps to a flaky network is an acceptable cost against the complexity of guaranteed delivery. No third-party analytics SDK (Segment, PostHog, etc.) for the same reason `CLAUDE.md`'s AI-cost discipline exists: another vendor, another script, another place user data leaves the household's own backend, for a volume of events a five-line ingest endpoint already serves.

**How to apply:** A fourth event type is a new zod variant in `analytics.ts` (mirror side) *and* a new branch in the route's discriminated union — both are required, or the new event 400s in production the first time it fires. If retry-on-failure or a reporting endpoint is ever justified by real volume, revisit both explicit non-goals above rather than bolting them on ad hoc.

## 2026-08-05 — Cooked-meal history: `cooked_meals`, and repeat-avoidance as a decaying penalty (#88)

**Table shape.** `cooked_meals` stores household_id, template_id, `substitution_key[]`, `cooked_at` and `cooked_on` — and deliberately *not* the conceptual `GeneratedMeal` + `SavedMeal` pair from ARCHITECTURE.md §5. There is no generated-meal row for a saved meal to point at (a Tonight suggestion is recomputed deterministically per request), so the only fact worth persisting is "this household cooked this template on this day"; §5 now describes what was built. `substitution_key` reuses `buildSubstitutionKey` from `src/db/recipeInstructions.ts` verbatim rather than re-encoding — one canonicalisation function for the codebase, and the slot-index-scoping rationale from the Tier 1 cache entry carries over. Nothing reads it yet: it is recorded because it is free now and impossible to reconstruct later. History is append-only — `matmatch_app` has SELECT and INSERT on this table and nothing else, so no bug can rewrite or erase a past evening. RLS inherits ownership through household_id, exactly as `household_members` does, with `matmatch_app` in every policy's TO clause (the 2026-08-03 trap).

**Idempotency is a constraint, not a query.** `unique (household_id, template_id, cooked_on)` plus `on conflict do nothing`, so a double tap of "Lagad ikväll" is one row and `POST /api/cooked` answers 200 with the first tap's timestamp — not 409, because the household did nothing wrong and the end state is what they asked for. The rejected alternative was read-then-insert against a `cooked_at > now() - interval '2 hours'` window: an extra round trip that also races two concurrent taps. `cooked_on` is a stored column defaulting to `(now() at time zone 'Europe/Stockholm')::date`, not a generated column — that expression is only STABLE, and generated columns require IMMUTABLE. Stockholm rather than UTC because a UTC day boundary falls at 01:00/02:00 local, inside the evening this table is about; Matmatch is Swedish-only for MVP (2026-07-29). Cost: a household cooking one dish twice in a day records one row. Tonight is dinner-only, so that case does not exist yet.

**Penalty, never a filter — and the numbers are derived, not chosen.** A recently cooked template is penalised in `scoreCandidate`, not excluded. A hard filter empties the candidate set for exactly the constrained households `selectCandidateTemplates` works to keep options for (all 8 allergies + vegan leaves 14 of ~170 templates), and an empty Tonight is the dead end UX_FLOW §9 forbids. `RECENCY_PENALTY_WEIGHT = 5.0` sits inside a band with both edges derived from existing constants: **above 4.75**, the entire score spread available at `DEFAULT_WEIGHTS` (two familiarity steps 3.0 + omnivore preference 1.5 + a full seasonality swing 0.25), which is what *guarantees* a dish cooked tonight ranks below every uncooked candidate for a household that has tapped nothing — the actual bug, three identical evenings in a row; and **below 6.0**, one maxed adjustment chip (weight 3) across a two-step cost/prep gap, so repeat-avoidance still yields to the strongest preference a household can express, the same property SEASONALITY_WEIGHT and FAMILIARITY_STEP_WEIGHT are calibrated for. `RECENCY_WINDOW_DAYS = 14` for two reasons: the resulting decay step (5.0/14 ≈ 0.36 per day) is just above SEASONALITY_WEIGHT, so ordering within the recently-cooked group is by recency rather than seasonality noise; and two weeks is roughly one household's whole dinner rotation. Past the window the penalty is exactly 0, not a residue. Both bounds are pinned by unit tests, so moving the weight out of the band fails the suite rather than quietly changing behaviour.

**Recency replaces the template-id tie-break, in `rankCandidates`'s comparator.** Least recently cooked first, never-cooked ahead of cooked, template id only as the last resort — which is what the placeholder comment there always said should happen once history existed. It lives in the comparator rather than in `pickNextSuggestion` so there is one ordering source of truth and Tonight and the guided flow cannot disagree about what "next" means. The penalty is quantised to whole days (a score should not drift hour by hour while someone reads the card), which is exactly why the tie-break still has work to do: two dishes cooked the same day score identically and are separated by the hour they were cooked.

**No history endpoint.** `GET /api/tonight` loads history server-side and hands it to ranking as data; the response exposes only `cookedToday` on the suggestion — the one fact the card needs so "Lagad ✓" survives a reload. A `recentlyCooked[]` list was drafted and cut: the client can render nothing else with it, and it would be ready-made API surface for the history screen that is explicitly out of scope. The engine stays pure — `RecencyContext` carries both the history map and `now`, so `src/engine/` still never reads the clock.

**How to apply:** Repeat-avoidance is a ranking signal, so future variety work (day-of-week, protein rotation, seasonal nudges) belongs in the score or the comparator alongside it — never as a filter on the candidate set, which is the one thing that can produce an empty Tonight. Before adding or changing a ranking constant, derive it against the existing ones and state both bounds at the definition site, as `RECENCY_PENALTY_WEIGHT`, `FAMILIARITY_STEP_WEIGHT` and `SEASONALITY_WEIGHT` now all do; a constant with no stated band is one nobody can safely change later. If any of those constants or the chip levels move, re-derive this one inside the new band rather than leaving it stale. For idempotent writes generally, prefer a unique constraint the database enforces over a time-window check the application performs.

## 2026-08-05 — Refinement stays chip-driven; no customize sheet, no cuisine filter, no user-facing difficulty (#82)

**Decision:** Session refinement on the Tonight card is expressed *only* through chips that each produce an immediately visible new suggestion — **Billigare** (+1 `cost`), **Snabbare** (+1 `time`), **Annat kök**, **Något annat**, **Återställ**. Chip state is visibly persistent for the whole session: a raised weight keeps its pressed styling and a 0–5 level marker (dots, with the level in the chip's accessible name — never conveyed by fill alone) until reset, so a household several rerolls deep can still see what it asked for. Increments cap at 5, and a tap at the cap is a genuine no-op that skips the request rather than re-fetching an identical dish. Reroll depth is instrumented (`web/src/analytics.ts`): one event per chip tap carrying the resulting weights and depth, one when a session ends without an acceptance carrying the final depth. Everything is React state — never the household profile, localStorage, or the database.

**Why, and what was rejected.** A chip tap and a slider notch write to the same `{cost, time}` vector, but only the chip shows its consequence per interaction — this is the 2026-07-31 sliders decision applied rather than re-litigated. `familiarity` is deliberately absent from the UI entirely, not merely from the chip row: the 2026-08-05 familiarity entry establishes it as a property of the dish, not a preference a household expresses per session, so a "simpler dishes" control would be a second, contradictory source of truth for the same ordering signal. **Cuisine is never a request parameter** — "Annat kök" resolves client-side to plain template-id exclusions (`searchOtherCuisine`, bounded at 4 probes, falling back to a plain reroll when no different-cuisine candidate remains). A cuisine parameter would be one short step from a multi-select that empties a ~170-template library, and it would add a filter dimension to an API whose whole selection surface is currently "ids I have already seen."

**The instrumentation is the load-bearing part, not a nice-to-have.** Repeated poor suggestions are either a *control* problem (the chips cannot express what the household wants) or a *coverage* problem (nothing in the library fits). More control surfaces hide that distinction instead of surfacing it. Chip taps plus final reroll depth are the minimum that tells the two apart in Phase 2; without them, the question gets settled by opinion later. Reroll depth is deliberately **not** zeroed by "Återställ" — reset restores the suggestion, not the friction the household already went through.

**Supporting call:** `exclude` and `previous` on `GET /api/tonight` now reject a *wrong-typed* value (a repeated parameter, which Express hands over as an array) with a 400 and a structured code, matching `parseWeightsFromQuery`. An *unknown or stale* template id is still silently ignored, and an over-long list is still truncated rather than rejected — those are legitimate states for a household whose constraints changed mid-session, and 400-ing them would dead-end a session that did nothing wrong.

**How to apply:** Route future refinement requests to a **new chip**, not a new control surface. Do not add a customize/anpassa sheet, sliders, a difficulty control, or a cuisine filter. Reopen the customize-surface question only if Phase 2 shows a meaningful share of sessions reaching reroll depth 4+ *while* the chip taps made fail to explain what the household was after — that combination is the evidence, not depth alone. The chip increment is 1 because that is exactly what `FAMILIARITY_STEP_WEIGHT` (1.5) is calibrated against; changing it means re-deriving that constant (see its comment in `src/engine/ranking.ts`).

**Superseded (same day, #86):** the 0–5 level marker and the cap-tap no-op described above were replaced by a two-level model (0/1/3, cycling back to 0 with no no-op) — see the entry above. Everything else here — chip-only refinement, no customize surface, cuisine resolved client-side, the instrumentation rationale — still stands.

## 2026-08-05 — First production AI call: Tier 1 cooking instructions (#78)

**Decision:** Tier 1 instruction generation (`src/ai/generateInstructions.ts`) calls **Claude Haiku 4.5** (`claude-haiku-4-5`), `max_tokens: 400`, a single stateless call with no conversation history, an 8-second client-side timeout, and structured JSON output (`output_config.format`) validated again with zod on receipt (`GeneratedInstructionsSchema`) — belt and braces, since structured output is a strong guarantee, not a proof. Haiku over a larger model because Tier 1 is templated personalization of an already-chosen dish (ARCHITECTURE.md §4.1), not open-ended generation — there is no reasoning task here that needs a bigger model, and this is exactly the routine-generation case §4.2 reserves the smaller tier for. 400 tokens comfortably covers 6–10 short Swedish sentences with headroom, without leaving the cap loose enough that a degenerate response runs long. 8 seconds is the "user is not left waiting" bound from a single screen transition (opening the shopping list), not a general API guideline — revisit only with real p95 latency data, not by feel.

**Cache key includes slot index, not only ingredient id.** The cache table (`recipe_instructions`, migration `20260805000000_recipe_instructions.sql`) keys on `template_id` plus a sorted array of `slot_index:substitute_ingredient_id` pairs, built once by `buildSubstitutionKey` (`src/db/recipeInstructions.ts`) and nowhere else. An id-only key was considered and rejected: two different slots swapped to the same ingredient id would collide under an id-only key, and this key is persisted — a wrong choice here means discarding the cache and re-paying generation cost for every row once the shape needs to change, while slot-scoping it now costs nothing. The no-substitution case still shares one row per template, per ARCHITECTURE.md §4.2's caching rule, since an empty substitution array sorts to an empty key regardless of which household asked.

**The endpoint never returns a 5xx for an AI failure, by contract, not by accident.** `POST /api/instructions` (`src/api/routes/instructions.ts`) treats a missing `ANTHROPIC_API_KEY`, a timeout, an API error, and a schema-invalid response identically: `200 { instructions: null, reason }`. Only a malformed *request* (unknown template, invalid substitution) is a 4xx — that distinguishes "the client asked for something that doesn't exist" from "the AI didn't come through," which must never block rendering the dish and shopping list the deterministic Meal Engine already produced. `generateInstructions` itself never throws — every failure mode inside it (timeout, network/API error, unparseable JSON, schema-invalid JSON) collapses to a typed `{ ok: false, reason }` result, so "never a 5xx" is enforced at the module boundary, not left to the route to remember on every call site.

**The cache table carries no RLS, unlike `households`/`household_members`.** `recipe_instructions` has no user id, no household id, and no per-row owner — it is keyed purely on template + substitution set, which is public-catalog-derived data, not personal data. RLS exists in this project to scope rows to the household that owns them (DECISION_LOG 2026-08-02/2026-08-03); a table with no owner column has nothing for a policy to scope against, so adding RLS here would be a policy that always evaluates the same way for everyone — mechanism without purpose. The 2026-08-03 grant/TO-clause trap (a policy silently matching no rows for a role, forever) accordingly doesn't apply: there's no policy to omit the role from. The migration only needs the explicit `GRANT` to `matmatch_app`, which it has, and the migration comment states the omission is deliberate so a future reader doesn't read the absence of RLS as a gap and add a pointless policy.

**How to apply:** Any future Tier 1 (templated-personalization) AI call should default to Haiku with the same never-a-5xx contract, not re-litigate the model choice per feature. Any future cache table keyed on a *persisted* composite that could plausibly need a finer-grained key later should default to the more specific key now — the cost asymmetry (free to add now, expensive to migrate later) generalizes beyond this table. Before adding RLS to a new table, check whether it has an owner column at all; if not, RLS is very likely a category error for that table, not a missing safeguard.

## 2026-08-05 — AI tiering, cost control and monetization sequencing

**Tier 2 is the fallback, not the coverage ceiling.** When a user asks for a dish the template library doesn't have, Tier 2 open-ended generation invents the dish. The template library (Tier 0) stays the free fast path that's supposed to cover the common case; Tier 2 exists to catch what it doesn't, not to be a second, AI-authored template catalog running alongside it.

**Hard rule: Tier 2 may invent the dish, never the ingredients.** Every ingredient in a Tier 2 response must resolve to an `ingredient_id` in `data/ingredients.json`; anything that doesn't map is dropped from the response, or the whole response is rejected if dropping it breaks the dish. This isn't a quality preference — allergen filtering (§4.3's fail-safe rule) resolves allergens per `ingredient_id`. A free-text ingredient the filter has never seen is invisible to it, and "invisible to the allergy filter" is exactly the failure mode §4.3 exists to prevent. There is no version of Tier 2 that's allowed to skip this.

**Caching: generated results are shared, personalization is not baked in.** A Tier 2 result is cached keyed on the normalized request phrase, with no household data in the key, so two households asking for the same thing share the cache entry. Personalization (swaps, portion math) is applied deterministically on top of the cache hit, not regenerated per household. Tier 1 instruction text is cached per template, matching how Tier 1 already works as templated personalization rather than open generation.

**Tier 2 output never auto-promotes into `data/recipe-templates.json`.** A generated dish staying popular is a signal, not a merge. Misses are logged; a repeated miss on the same dish is what triggers a deliberate, reviewed template batch using the #10–14 coverage-matrix method — the same authoring and evidence bar every existing template went through, not a shortcut around it.

**Tier 2 ships with a per-user monthly cap and a global spend ceiling, or it doesn't ship.** Both degrade to Tier 0 plus cache when hit, never to a failure or to unmetered spend. This is the cost-control half of §4's tiering strategy actually being load-bearing rather than aspirational.

**Web scraping of recipe sites is rejected as an ingredient/coverage source.** Scraped ingredients arrive with no verified allergen mapping row — the same problem free-text Tier 2 ingredients would have, for a data source that also carries copyright exposure and ongoing scraper-maintenance cost for no offsetting benefit over generation-then-cache.

**Monetization sequencing: freemium caps on Tier 2 are the MVP revenue mechanism; ads are deferred to Phase 3.** Ads add a second, unrelated product surface and revenue path before there's evidence anyone wants the core loop enough to pay for it. Revisit trigger: measured premium conversion plus several thousand active users — not a fixed date.

**Feedback is binary (thumbs up/down), not a 1–5 star scale, and personal before global.** Binary needs no calibration and is useful starting from a single user's first rating; a star scale only means something once there's enough volume to normalize against, which the MVP doesn't have yet. Personal feedback (did *this household* like this suggestion) feeds ranking immediately; global aggregation is a later layer once there's enough signal for it to be meaningful.

**How to apply:** do not build Tier 2 without both the ingredient-mapping hard rule and the spend caps in place together — neither is optional, and shipping one without the other reintroduces the exact risk (unsafe suggestion, or unbounded cost) tiering was supposed to prevent. Do not reach for scraping as a coverage shortcut if Tier 2 generation feels slow to build out — the reasons it was rejected apply regardless of how tempting the ingredient volume looks.

## 2026-08-05 — `DEFAULT_WEIGHTS` becomes `{cost: 0, time: 0}`; an omnivore preference is added alongside it

**Decision:** `DEFAULT_WEIGHTS` (`src/api/weights.ts`) changes from `{cost: 1, time: 1}` to `{cost: 0, time: 0}`. This corrects the 2026-07-31 "Rejected user-facing priority sliders" entry rather than reversing it: that entry's own text calls `{cost: 1, time: 1}` "an assumed starting point, not a claim about what any household wants," and dogfooding showed the assumption was doing real, unwanted work — the weight vector is supposed to express what the household asked for *this session*, and a household that has tapped nothing has asked for nothing. Because `cost_tier` correlates with `dietary_tags` in the catalog (lentils, chickpeas, beans are budget tier almost throughout), a standing cost preference nobody expressed was quietly also acting as a standing vegetarian preference — the two symptoms (skews cheap, skews vegetarian) shared this one root cause. At the new default, familiarity and seasonality alone decide, matching the zero-input Tonight behavior UX_FLOW §9 already specifies for a new user with no history.

**A second, independent root cause needed its own fix:** nothing in the engine encoded that a household without a declared `vegetarian`/`vegan` flag mostly eats meat. `scoreCandidate` (`src/engine/ranking.ts`) now takes the household's `dietary_flags` and adds `FAMILIARITY_STEP_WEIGHT` (one familiarity step, not a new constant) to any candidate tagged `vegetarian` or `vegan` in `dietary_tags`, unless the household itself declared one of those flags — in which case the penalty is zero. This is ranking-only, same shape as the familiarity fix: `selectCandidateTemplates` is untouched, so a vegetarian template is never excluded for an omnivore household, only made to compete on cost/season/familiarity like everything else.

**`FAMILIARITY_STEP_WEIGHT = 1.5` did not need to change, but its calibration story did.** It was documented as calibrated "against `DEFAULT_WEIGHTS = {cost: 1, time: 1}`," which stops making sense once the default is zero. The actual invariant was always about a chip-raised weight of 1 (the first "cheaper"/"faster" tap), which the old defaults happened to equal — so the constant is unchanged, only its comment and the mirroring 2026-08-05 familiarity entry's framing are corrected to name the real thing they depend on.

**Data corrections, same session:** `pannkakor-med-vaniljsocker` and `artsoppa-med-senap` lose `"dinner"` from `meal_types` (both keep `breakfast`/`lunch` as applicable). This is the same kind of low-evidence-bar correction that entry's evidence-bar paragraph already anticipates — a wrong `meal_types` value costs one repeated bad suggestion, not a safety issue.

**How to apply:** do not re-derive `DEFAULT_WEIGHTS` back toward a nonzero value to "smooth out" a thin candidate set — that is what the omnivore and familiarity penalties exist to do instead, without silently assuming a budget preference. ## 2026-08-05 — RecipeTemplate gains `familiarity`, authored not derived; ranking-only, never a filter

**Decision:** `RecipeTemplate` gains a required `familiarity: "everyday" | "occasional" | "adventurous"` field, no default (#72). All 170 rows were retroactively classified in one pass by reading each dish's name and `ingredient_slots`, using "would a typical Swedish household cook this on an ordinary weekday" as the test; ties between two levels were resolved toward the *less* familiar one, since a dish wrongly marked `everyday` shows up unprompted — the exact failure being fixed. `scoreCandidate` (`src/engine/ranking.ts`) adds a penalty of `familiarityIndex(familiarity) * FAMILIARITY_STEP_WEIGHT` (everyday 0, occasional 1, adventurous 2 steps), same shape as the existing cost/time/seasonality terms. It is a ranking signal only: `selectCandidateTemplates` is untouched, so an adventurous template is never excluded from the candidate set, only ordered lower by default.

**Why authored, not derived, and why not in the session weight vector:** same rationale as `meal_types` below — how familiar a dish is to a typical household is a judgment call about the dish as a whole, not computable from `ingredient_slots[]`. It is also deliberately *not* part of `RankingWeights` (`{cost, time}`, DECISION_LOG 2026-07-31): familiarity is a property of the dish, not a preference a household expresses per session, so a chip cannot and should not move it.

**`FAMILIARITY_STEP_WEIGHT = 1.5`, calibrated explicitly against `DEFAULT_WEIGHTS = { cost: 1, time: 1 }`** in `src/api/weights.ts`, not chosen in isolation the way `SEASONALITY_WEIGHT` was. At those defaults, one familiarity step (1.5) already beats one cost-tier or prep-band step (1), and the full two-step gap (3.0) beats two — closing the concrete gap this slice exists to fix: a cheap unusual dish (e.g. `musselgryta`, budget/adventurous) no longer outranks an ordinary one (e.g. `köttbullar`, mid/everyday) just because a household asked for "cheaper." A weight of 0.5 was considered and rejected: it would only let a two-step familiarity gap *tie* a single cost-tier step, so a budget adventurous dish could still beat a mid everyday one — reproducing the bug. It is still not unbeatable: a chip pushing cost or time weight to 3+ lets that expressed preference dominate again, mirroring how `SEASONALITY_WEIGHT` is designed to yield to a real preference. If `DEFAULT_WEIGHTS` ever changes, this constant must be re-derived against the new default, not left calibrated to a stale one.

**Evidence bar:** same as `meal_types` — single AI-judgment pass, not independently verified against any source. A wrong `familiarity` value costs one repeated bad suggestion, not a safety issue, so the allergen-mapping bar (100%-manual, two-pass, DECISION_LOG 2026-07-31) does not apply here. The full classification (every `everyday` and `adventurous` call, grouped by `protein_group`, plus per-group counts) is recorded in PR #72's description, not here, for the same reason the `meal_types` exclusion list lives in PR #67's description — a 170-row judgment pass is reviewable as a list, not a summary count.

**How to apply:** A new recipe template must set `familiarity` explicitly at generation time — no default, so a template can't silently inherit `everyday`. Do not add a `familiarity` consistency check to the validator: like `meal_types`, there is nothing in `ingredient_slots[]` to derive or check it against.

## 2026-08-03 — Backend connects as a least-privilege role; RLS is now load-bearing (corrects the entry below)

**Correction first, because the entry below names the wrong mechanism.** It says a **superuser** connection bypasses RLS. In this project's database no such connection exists: `postgres` has `rolsuper = false` and `rolbypassrls = true`. The practical effect described was right — policies did not constrain the backend — but the attribute responsible was `rolbypassrls`, not superuser status. Left uncorrected, a reader auditing this would go looking for a superuser that isn't there and conclude the note was stale. The entry below is not edited; this is the correction of record.

**Decision:** The backend no longer connects as `postgres`. It connects as **`matmatch_app`** — `nosuperuser`, `nobypassrls`, `nocreatedb`, `nocreaterole`, no `CREATE` on any schema, and grants on exactly the two household tables and nothing else. Repository calls run inside a transaction that first sets the request's authenticated user as the RLS claim (`set_config(..., true)`, transaction-scoped so a pooled connection cannot carry one user's identity into the next request). Missing user context **throws** at the repository boundary rather than returning an empty result, so a programming error surfaces as an error instead of a plausible-looking 404; the database independently returns zero rows for an uncontexted query, and both layers are tested separately.

Two supporting calls worth recording. **Policies now name the role in their `TO` clause** (`to authenticated, matmatch_app`); the `USING`/`WITH CHECK` predicates are untouched. The alternative — granting `matmatch_app` membership in `authenticated` — was rejected because it would inherit Supabase's `ALTER DEFAULT PRIVILEGES` on `authenticated`, silently auto-granting access to every future table and defeating the point of the least-privilege role. And **the role is created without a password**: a password in a committed migration is a credential `supabase db push` installs in production, so the local password lives in `supabase/seed.sql` (never pushed) and the cloud one is set by hand. No password means no connection, which fails closed.

**Why this had to land before the first HTTP endpoint:** until now, "the backend authorizes its own queries" had nothing underneath it. A missing `where owner_user_id = ...` in one repository function would have leaked another household's data — including allergies, which ARCHITECTURE.md §7 treats as health-adjacent personal data — with nothing to catch it. The endpoint slice is where such a mistake first becomes reachable from outside, so the second line had to exist first.

**How to apply — the trap this creates.** There is deliberately no `ALTER DEFAULT PRIVILEGES`, so **every new table needs both an explicit grant to `matmatch_app` and the role added to each of its policies' `TO` clause**. Missing the grant fails loudly (`permission denied`); missing the `TO` entry does not fail at all — the backend reads zero rows silently, forever. That asymmetry is why the warning is duplicated in the migration file and in README.md's migrations section rather than recorded only here. `DATABASE_URL` must never point at `postgres`, `supabase_admin`, or a service-role connection; all three carry `rolbypassrls` and would turn household scoping off without any error. A test in `src/db/rls.test.ts` asserts `matmatch_app` carries neither attribute, and a separate one still documents that a `rolbypassrls` connection does bypass policies — kept, because that remains true of Postgres and is the whole reason this role exists.

## 2026-08-02 — Supabase for both database and auth (closes the two 2026-07-28 open items)

**Decision:** Hosting/DB provider and auth provider are **both Supabase**, decided as one call rather than two — they are coupled, and splitting them (Neon + Auth.js) means "who is this user" and "which rows may they see" are enforced in different systems that have to agree. Region is **`eu-north-1` (Stockholm)**, fixed at provisioning: allergy data is sensitive personal data under GDPR (ARCHITECTURE.md §7), and a Supabase project's region cannot be changed afterwards — moving it is a new project plus a migration, not a setting. Five conditions are part of the decision, not implementation detail:

1. **The Node backend is the only path to household and meal data.** The project's Data API (PostgREST) is **disabled** and "automatically expose new tables" is off, so this is enforced at the platform level rather than by convention. Adopting the client → RLS → Postgres idiom would let the frontend read recipe data directly, which makes the Meal Engine's allergy filtering (§4.3) skippable by a client bug.
2. **RLS is enabled and FORCEd on household tables as defense-in-depth, never as the mechanism the backend relies on.** See the limitation below — this is deliberately not load-bearing.
3. **Auth is a thin adapter:** bearer token → user id, nothing else. JWT signing is **asymmetric (ES256)**, verified against the JWKS endpoint with `jose` and an in-memory key cache. `@supabase/supabase-js` is **not a dependency** — data access is plain `postgres.js`. The backend holds no signing secret and no service-role key; it only ever verifies.
4. **Migrations are plain SQL** in `supabase/migrations/`, no ORM schema layer (no Drizzle/Kysely). RLS policies must live in SQL regardless, and a second schema notation on top would put the schema in two places — the exact problem this decision avoids elsewhere.
5. **Free-tier projects pause after ~7 days of inactivity.** Expected during intermittent solo work, not an outage. Documented in README.md, where it will actually be read when connections start timing out.

**Why Supabase over Neon:** managed auth removes session/token/password-reset code that would otherwise be written and maintained solo, and Supabase's JWT is understood by Postgres itself, so household-scoped access control is one mechanism rather than two. Neon's real edge — fast database branching for heavy multi-environment schema experimentation — is a team-scale benefit that does not apply to a solo, pre-schema-lock project. Both are mainstream managed Postgres; neither is exotic, and nothing here uses Postgres in a way that would constrain a later move.

**Limitation, stated explicitly so it is not mistaken for protection it does not give:** RLS guards against a *direct database client* — someone with the connection string, or a future re-enabled Data API. It does **not** guard against a bug in the backend. `FORCE ROW LEVEL SECURITY` closes the table-owner bypass, but a **superuser connection bypasses policies entirely**, and the backend currently connects as `postgres`. A test in `src/db/rls.test.ts` asserts this bypass on purpose, so the boundary is visible in the suite rather than assumed. Making the backend connect as a dedicated least-privilege role — which would make RLS genuinely load-bearing — is filed separately; until then, authorization is the backend's job and RLS is a second line only.

**How to apply:** Do not re-enable the Data API to "just query from the frontend," and do not reach for `supabase-js` for data access — both would route around §4.3. Keep `@supabase/supabase-js` out of `package.json` unless something genuinely needs the SDK; JWT verification does not. Reversal cost is bounded by the thin adapter: a different issuer is a different JWKS URL, and the schema is portable plain SQL. ## 2026-08-01 — Protein slots stay non-substitutable; ingredient-swap variety rests on the other four roles

**Decision:** All 170 recipe templates have exactly one protein slot, and in all 170 it is `substitutable: false`. That stays. ## 2026-08-01 — Substitutions are symmetric groups, not directed pairs (ARCHITECTURE.md §5.5)

**Decision:** A substitution is a `SubstitutionGroup` — `{id, name (Swedish display text), role (reuses `IngredientSlotRole`), member_ingredient_ids[]}`, minimum 2 members, no duplicates within a group, an ingredient may belong to several groups. Not directed `(from, to)` pairs. The group carries **no** allergen or dietary field of any kind, no similarity/quality score, no canonical or preferred member, and no reverse index. `ingredient_slots[].substitutable: false` suppresses swaps for that slot regardless of group membership. Stored as `data/substitutions.json`, validated as `--type substitution`. No substitution data was generated in this issue — the file stays an empty array.

**Why:** A 4-member group is 12 directed pair rows, each an opportunity for the data to contradict itself ("gul lök → rödlök" existing while the reverse doesn't). The group is also the unit the UI consumes — the swap sheet shows *the other members*, a set operation, not a graph traversal. The real cost of groups is that they assert **symmetric** interchangeability and cannot express that one direction is worse (tofu for chicken is fine; chicken into a tofu-authored dish changes what the dish is). That was accepted deliberately: which member to prefer is a per-household, per-session ranking judgment the Meal Engine owns — and which the session weight vector from the 2026-07-31 priorities decision already exists to carry — not a static property of the data that would compete with it. Allergen/dietary fields are excluded because a suitability claim on a group is a second source of truth for safety-critical filtering (§4.3): hand-curated, unversioned against the §5.4 mapping, and able to read as "safe" for a member whose mapping row is missing or `unverified`, routing straight around the fail-safe rule.

**How to apply:** Reversal is cheap in one direction only — groups decompose into pairs mechanically; pairs do not recompose into groups without re-deriving which sets are mutually interchangeable. So if authoring real data (a later issue) turns out to need direction, converting then costs little; adopting pairs pre-emptively cannot be undone as easily. Do not add a cost-tier consistency check across group members: groups are most useful when members differ in tier (the premium→budget swap is the feature), and enforcing homogeneity would delete it.

**Unresolved, deliberately — swap drift against the derived `cost_tier` rule.** The 2026-07-31 entry below makes `RecipeTemplate.cost_tier` the highest `default_cost_tier` among slot ingredients, validator-enforced. That rule holds **only for the exact ingredient set in `ingredient_slots[]`**: the stored tier describes the canonical template, not the meal after a swap. A user who swaps premium lax for mid torsk keeps looking at a ₤₤₤ badge — a curated number drifted from its source of truth, precisely the failure the derived-field rule was written to prevent. **A swapped meal's effective cost tier is undefined until Phase 1.** Two candidate resolutions exist — recompute the effective tier at swap time, or store the canonical tier plus a derived range — and neither is chosen here; this is a Meal Engine call to make when it first renders a tier for a swapped meal. Recorded here rather than as a GitHub Issue on purpose: there is no Phase 1 Meal Engine issue to attach it to, so a ticket filed now would sit unmilestoned in Backlog and rot, whereas this log is read at the moment the question becomes actionable.

## 2026-07-31 — Manual allergen verification method (#27–#29): two-pass, label-backed, tiered evidence bar

**Decision:** #9's 100%-manual-verification pass used a fixed two-pass method across all three sub-issues, reusable as the catalog grows. **Pass 1 (raw):** every row is first classified raw (a single unprocessed ingredient whose allergen set follows from what it is) or manufactured (a recipe/processed product), per the plain-form rule already logged above. Raw rows are grouped into rule blocks (e.g. "fresh vegetables → `[]`", "plain fish → `fish`") and confirmed as a block, not row by row. **Pass 2 (manufactured):** every manufactured row — tagged or not — is verified against an actual retail label (ICA.se/Coop.se, mainstream own-brand or market-leader, not premium/organic/specialty-importer), Innehållsförteckning quoted verbatim. Evidence bar, asymmetric by design: **one label is sufficient to confirm or add an allergen; two independent manufacturers are required to remove `gluten`, `dairy_lactose`, `egg`, or `soy`; three independent manufacturers are required to remove `shellfish`, `fish`, `peanuts`, or `tree_nuts`** — the higher bar for the second group reflects that removal-error consequence scales with reaction severity, not just row count. A "Kan innehålla spår av" trace warning collapses into `allergens[]` exactly like a definite ingredient, per §5.4 — never a separate `may_contain` state. Every outcome is recorded as one of four categories: **correction** (label contradicts the draft), **confirmation** (label agrees), **held-not-removed** (insufficient evidence to remove; kept fail-safe, evidence gap stated explicitly so it's revisitable), or **formulation split** (brands genuinely differ; tag kept fail-safe as an accepted, known coverage cost — not an error).

**Why:** A second independent AI draft (`tmp/allergen-review-worksheet.md`, pre-#27) found disagreements concentrated entirely in manufactured products and none in raw ones, so raw-row risk is low and manufactured-row risk carries effectively all of it — the two-pass split routes human attention accordingly without reducing coverage (every row, raw or manufactured, still gets an explicit ruling). Two headline findings justified the label-backed rigor over a lighter spot-check: (1) the AI draft **systematically assumed continental (wheat-and-soy) formulations for Swedish charkuteri, korv, and bread** — wrong across 6 brands and 3 product classes (skinka/rökt skinka, falukorv/grillkorv, formbröd all had incorrect gluten/soy/dairy tags; Swedish binders are potato-starch-based, not wheat/soy). (2) `pesto` was **missing an allergen entirely** (`egg`, via declared lysozyme/cheese in a mainstream label) — a different and more dangerous failure direction than over-tagging, since an invented allergen only costs a household an unnecessarily avoided dish, while a missing one tells an allergic household a dish is safe when it isn't. Finding #2 is the concrete reason CLAUDE.md's no-sampling rule is correct as written: a spot-check tuned to catch over-tagging (the more common and more "visible" failure) would not have caught this.

**How to apply:** Reuse this exact method for any future ingredient-allergen verification (new catalog rows, a vocabulary expansion). Do not sample even when a batch looks low-risk — pesto's missing egg is the standing counter-example. Two rows are currently `held-not-removed` and need revisiting rather than re-deriving from scratch if new evidence appears: **`blodpudding`** holds `dairy_lactose` and `egg` — only one Swedish manufacturer (Gea's/Lithells, both part of Atria) could be found, gluten is separately confirmed and stands; clears if a second independent manufacturer's label is found and agrees or disagrees. **`worcestershiresas`** holds `soy` — Lea & Perrins is effectively the only Worcestershire sauce sold in Swedish mainstream retail, `fish` and `gluten` are separately confirmed and stand; clears the same way if a second brand is ever stocked. Also recorded: `tree_nuts` and `peanuts` are now coextensive on every packaged nut row in the catalog, because Swedish nut-packing uses shared processing lines and the trace-collapse rule is binding — this is the collapse rule (§5.4, 2026-07-31 entry above) working as designed, and it is the first concrete evidence for the graded-risk revisit that entry flagged as a possible future cost. It is evidence, not a trigger — do not reopen the collapse decision on the strength of this alone.

## 2026-07-31 — Locked ingredient-to-allergen mapping schema (ARCHITECTURE.md §5.4)

**Decision:** The ingredient→allergen mapping (issues #8/#9's source data) is a **separate** entity, `IngredientAllergenMapping`, not a field on `Ingredient` (§5.1) — one record per ingredient (`ingredient_id`, `allergens[]`, `verification_status`), not one per `(ingredient, allergen)` pair. `verification_status` is a required two-value enum (`unverified` / `verified`), with no `verified_by`/`verified_at` fields. "May contain" / cross-contamination cases (oats and gluten, sausage fillers) are collapsed into `allergens[]` — there is no third `may_contain` state. Stored as its own file, `data/ingredient-allergens.json`, validated via #15's CLI as `--type ingredient-allergen`, which adds a coverage check (every catalog ingredient must have a mapping row, erroring when missing) and reports an unverified-row count as a warning in its summary.

**Why:** One row per ingredient is the only shape that can express "verified, contains nothing" without ambiguity — with per-pair rows, zero rows for an ingredient is indistinguishable between "confirmed allergen-free" and "never reviewed," which is exactly the silent-allergen-free failure this schema exists to prevent (CLAUDE.md's 100%-manual-verification non-negotiable). It also matches how a human actually reviews (#9): one ingredient's full profile per pass, not scattered pair-rows. A separate entity (not inline on `Ingredient`) gives the mapping its own verification lifecycle, keeps it reviewable as a bounded ~200-row artifact independent of the full catalog, and stops an unrelated `Ingredient` edit (e.g. a cost-tier correction) from silently riding along with an unreviewed allergen change. Collapsing "may contain" into `allergens[]` is the fail-safe-correct call for a **hard binary exclude** filter (§4.3) — both cases require identical downstream behavior (exclude), so a graded third state would add real modeling weight for a distinction nothing in the current product consumes. `verified_by`/`verified_at` were left out because git blame and PR review on this file already own that information; adding it to the row would be a second source of truth for something git already tracks.

**How to apply:** #8 (generation) writes rows with `verification_status: "unverified"`; #9 (verification) is the only thing allowed to flip a row to `"verified"`, and must review 100% of rows — no sampling, per CLAUDE.md. Any Meal Engine code that consumes this mapping (not yet built) must treat a **missing row** and an **`unverified` row** identically to a row that **contains** the allergen — both exclude the ingredient for a household with that allergy; never default to permissive on absence or non-verification. Collapsing "may contain" into `allergens[]` is **lossy, not free to reverse**: if graded allergen risk is ever genuinely needed (most likely trigger: gluten-free-*by-choice* users complaining they lose oats unnecessarily, as already flagged as a deferred dietary-flag gap in the §5.2 decision), undoing it costs a full manual re-review pass over every row currently containing `gluten`, `tree_nuts`, or `soy` — sausages, oats, and anything else marked via the "may contain" convention need re-classifying into "definite" vs. "may contain" by a human, since that distinction was never captured. It is not a schema migration; it's a second full verification pass over roughly a third of the catalog. Budget for that explicitly rather than assuming a field can just be added.

## 2026-07-29 — Cost-tier enum values changed from glyphs to words; id fields constrained to ASCII slugs

**Decision:** `Ingredient.default_cost_tier` / `RecipeTemplate.cost_tier` data values changed from `₤`/`₤₤`/`₤₤₤` to `budget`/`mid`/`premium`. **Why:** `₤` is U+20A4 LIRA SIGN, visually near-identical to `£` U+00A3 POUND SIGN — a homoglyph error in ~420 rows of generated data (#6, #10-14) would be effectively invisible in review and would corrupt grep, URL params, CSV export, and DB indexing, for a symbol that means nothing to a Swedish user in the first place. The catalog is authored in Swedish (gul lök, fläskfilé, kantareller); an unconstrained `id` would inherit åäö and risk NFC/NFD normalization mismatches in the same class of places — worse, since two visually identical `ö` can be different byte sequences. Both were caught and fixed before any real data existed, at effectively zero migration cost.

**How to apply:** Frontend cost-tier rendering must map the enum value to a glyph in display code, never reuse `budget`/`mid`/`premium` as if it were the glyph. Ingredient/recipe-template generation (#6, #10-14) must derive `id` as a slug of the Swedish `name` (transliterated, not truncated) rather than an arbitrary counter — see the corresponding issue bodies for the explicit requirement. As of the Tonight card (#64/#65 follow-up), the frontend renders cost tier as a three-dot meter with a Swedish `aria-label` rather than the `₤` glyph described above — do not reintroduce the lira sign in display code; the exhaustive-switch requirement (a new tier must fail typecheck) applies to whichever display form is current.

## 2026-07-29 — Locked RecipeTemplate schema; coverage matrix scoped by realism, not full cross-product

**Decision:** `RecipeTemplate` reuses the `Ingredient` cost-tier enum (§5.1) and the `dietary_flags` vocabulary (§5.2) rather than defining parallel ones; adds its own `protein_group` (5 values, matching issues #10-14 exactly) and `cuisine` (6 broad values) enums. ## 2026-07-29 — Locked allergy & dietary-flag vocabulary; scoped deliberately narrow for MVP

**Decision:** `allergies[]` (hard filter): `gluten`, `dairy_lactose`, `egg`, `tree_nuts`, `peanuts`, `shellfish`, `fish`, `soy` — not the full EU 14-allergen list. `dietary_flags[]` (soft preference): `vegetarian`, `vegan`, `high_protein_preference`, replacing the separate `protein_preference` field. **Why:** Scoped to what MVP actually needs (UX_FLOW.md's onboarding chips, the "vegetarian & vegan" template batch) rather than the maximal correct list, per explicit direction to avoid over-expanding the taxonomy pre-PMF. Two things were deliberately deferred rather than added speculatively: gluten-free-by-choice (currently only expressible as the stricter `gluten` allergy — fine for MVP, revisit if lifestyle users complain) and religious dietary restrictions (halal/kosher/no-pork) — plausible for the Swedish market but not part of the current MVP use case, and would need a decision on hard-filter vs. soft-preference treatment before being added, not a snap call. Family-friendly cooking is derived from household composition (`type: child` present) rather than a new flag, to avoid a second source of truth for the same signal.

**How to apply:** If real usage surfaces demand for any deferred item (pescatarian, gluten-free-as-preference, halal/kosher, sesame/celery/mustard allergies), add it as a new controlled-vocabulary value, not a schema change — `allergies[]`/`dietary_flags[]` are already open arrays. Religious dietary restrictions specifically should get their own scoping discussion (hard vs. soft) before being added, not be folded into the existing lists by default.

## 2026-07-29 — Locked Ingredient schema (category taxonomy, cost tiers, seasonality fields)

**Decision:** Ingredient category is an 8-value enum by culinary usage (`protein`, `vegetable`, `fruit`, `dairy`, `starch`, `spice_aromatic`, `fat_oil`, `condiment`) rather than the 6 suggested in issue #1's original text. Seasonality is `peak_months[]` (1-12) + `available_year_round` (boolean) + `seasonality_strength` (`strong`/`weak`), rather than a single loose `seasonality_tags[]` string array or coarser season-name tags. Full definitions and known edge cases (legumes, mushrooms, nuts) are in [ARCHITECTURE.md §5.1](../ARCHITECTURE.md#51-ingredient-schema-locked-phase-0-day-1).

**Why:** A 20-ingredient spot-check against the original 6-category draft failed on cooking oils and fruit — both common in Swedish home cooking, neither fitting `condiment` or `vegetable` without creating semantically wrong groupings that would misfire once recipe templates start matching on category. Category is by culinary usage, not botany/nutrition, since that's what the Meal Engine actually reasons about. For seasonality, month-level granularity plus a year-round/strength split gives the Meal Engine a computable "in season now" signal and separates a hard seasonal cutoff from a soft price/quality one, at only marginal extra curation cost over a coarser scheme.

**How to apply:** Ingredient catalog generation (issue #6) should categorize by function-in-a-dish, not ingredient type — e.g. chickpeas/lentils/tofu are `protein`, mushrooms are `vegetable`, nuts default to `condiment` unless a specific template uses them as the protein base (a template-level tagging call, not a reason to recategorize the ingredient). Split generic catalog entries ("svamp", "lök") into specific varieties wherever cost tier or seasonality genuinely differs between them.
